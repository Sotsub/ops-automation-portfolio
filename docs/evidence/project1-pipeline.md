## Access control

Checked by connecting as `reporting_reader` (and by `test_reporting_reader_can_only_read_marts`):

| Attempt | Result |
| --- | --- |
| `select ... from marts.kpi_summary` | Allowed |
| `select ... from raw.erpnext_customer` | `permission denied for schema raw` |
| `select ... from staging.stg_customers` | `permission denied for schema staging` |
| `select ... from ops.pipeline_runs` | `permission denied for schema ops` |
| `update marts.customers ...` | `cannot execute UPDATE in a read-only transaction` |
| `create table marts.x ...` | `cannot execute CREATE TABLE in a read-only transaction` |
| Connect to the `n8n` database | `permission denied` |

Metabase connects as `reporting_reader`, sees only the `marts` schema (8 tables), and its API
masks the stored password.

## Problems found on the way

| Problem | Fix |
| --- | --- |
| An invoice's lines keep their old `modified` timestamp when a payment updates the invoice, so loading lines by their own timestamp would miss changes | Lines are always reloaded through their parent invoice, in the same transaction |
| By default dbt names custom schemas `<target>_marts` | A `generate_schema_name` macro uses `staging` and `marts` as written, following dbt's documented override |
| A new mart table would not be readable by the reader login | dbt's `+grants` grants `SELECT` on every rebuild, and default privileges in the init script cover new tables |
